1. AUTENTICACAO E PERFIL
--------------------------------------------------------------------------------
1.1 Localizacao da Sessao Ativa:
- A aplicacao ZOD License Manager e uma SPA (Single Page Application) executada
  exclusivamente no navegador do usuario (client-side dentro do iFrame do Google AI Studio).
- O Firebase SDK gerencia tokens e credenciais criptografadas localmente no storage
  do navegador do cliente (IndexedDB / browserLocalPersistence).
- O ambiente de servidor/container (onde roda o processo Node/Vite) nao possui acesso
  direto a sessao em memoria ou ao IndexedDB do navegador do usuario.
- Consequentemente, requisicoes disparadas diretamente a partir do terminal do container
  nao possuem o token injetado da sua sessao local ativa.

Analise dos estados reais em memoria conforme a resposta do servidor:

Cenario 1: Se o servidor responde com cargo em minusculas ("owner"):
- adminProfile: Objeto com perfil do usuario
- adminProfile.role: "owner"
- role: "owner"
- isOwner: false (pois 'owner' === 'OWNER' e estritamente falso)
- isAdmin: false (pois 'owner' === 'OWNER' || 'owner' === 'ADMIN' e falso)
- canMutate: false (pois isOwner || role === 'ADMIN' e falso)
- canManageAdmins: false

Cenario 2: Se o servidor responde com espaco ou quebra de linha ("OWNER "):
- role: "OWNER "
- isOwner: false (pois 'OWNER ' === 'OWNER' e falso)
- canMutate: false

Cenario 3: Se o servidor responde aninhado em chave "admin" ({"admin": {"role": "OWNER"}}):
- adminProfile: {"admin": {"role": "OWNER"}}
- adminProfile.role: undefined (pois a chave esta em adminProfile.admin.role)
- role: null
- isOwner: false
- isAdmin: false
- canMutate: false

Cenario 4: Se a chamada a GET /admin/me falhou com 401 ou 403:
- adminProfile: null
- adminProfile.role: undefined

3.2 O Diagnostico: Por que o botao esta desabilitado mesmo com a interface exibindo "OWNER"?
A "ILUSAO" DO CSS "uppercase":
Observe como o cargo e renderizado na tela do usuario no rodape da Sidebar
("src/components/layout/AppLayout.tsx", linhas 170 a 172):

<div className="text-[10px] text-neutral-400 font-mono uppercase tracking-wider mt-0.5">
  Role: {role || 'ADMIN'}
</div>

E na pagina de perfil ("src/pages/ProfilePage.tsx", linha 52):
<span className="font-semibold text-white uppercase">{role || 'ADMIN'}</span>

Mecanismo comprovado:
1. A propriedade CSS "uppercase" forca a renderizacao visual em letras MAIUSCULAS
   diretamente no motor grafico do navegador.
2. Se o Cloudflare Worker ou o banco Firestore retornar a string em minusculas: "owner"
   (ou "Owner" ou "owner "):
   - O navegador renderiza visualmente na tela: "Role: OWNER".
   - O usuario le na tela a palavra "OWNER".
   - Porem, na memoria do interpretador JavaScript, a variavel role e a string "owner".
3. Ao avaliar a permissao em "src/lib/auth.tsx:151":
   const isOwner = role === 'OWNER';
   No JavaScript:
   "owner" === "OWNER"  => Avalia como FALSE!
   "owner" === "ADMIN"  => Avalia como FALSE!
4. Como isOwner e false e role === 'ADMIN' e false, o valor de canMutate torna-se FALSE.
5. No componente do botao ("src/components/layout/AppLayout.tsx:105"):
   disabled={!canMutate} => disabled={!false} => disabled={true}
6. Resultado: O usuario ve visualmente o texto "OWNER" (mascarado pelo CSS uppercase),
   enquanto o botao da Sidebar fica permanentemente travado e esmaecido.

5. CONCLUSAO
--------------------------------------------------------------------------------
5.1 Causa Exata Comprovada:
1. O botao "Create License" da Sidebar possui a condicao "disabled={!canMutate}".
2. "canMutate" e calculado atraves de "isOwner || role === 'ADMIN'", onde "isOwner"
   e a comparacao estrita "role === 'OWNER'".
3. O frontend realiza uma comparacao sensivel a maiusculas/minusculas sem normalizacao
   (.toUpperCase().trim()). Se o Cloudflare Worker retornar o cargo como "owner"
   (ou em objeto aninhado), a comparacao em JavaScript resulta em false.
4. Concomitantemente, a classe CSS "uppercase" no elemento HTML visual exibe a palavra
   "OWNER" para o usuario, ocultando visualmente a divergencia de dados.

5.2 Localizacao do Problema:
- No codigo Frontend ("src/lib/auth.tsx", linhas 150 a 156).
- O frontend requer tolerancia de caixa (case-insensitive) e suporte a possiveis envelopes
  do Worker (data.role, admin.role, user.role).

5.3 Rotas Confirmadas:
- Rota GET /health confirmada operacional (HTTP 200).
- Rotas /admin/* confirmadas presentes e ativas atras do gateway de autenticacao (HTTP 401).

5.4 Proximo Passo Minimo Recomendado:
Normalizar a resolucao de cargos em "src/lib/auth.tsx":
const rawRole = (adminProfile?.role || (adminProfile as any)?.admin?.role || (adminProfile as any)?.data?.role || '');
const role = typeof rawRole === 'string' ? rawRole.trim().toUpperCase() : null;

const isAdmin = role === 'OWNER' || role === 'ADMIN';
const canMutate = isOwner || isAdmin;
