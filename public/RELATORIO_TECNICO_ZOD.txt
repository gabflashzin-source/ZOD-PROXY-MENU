1.3 Como o Frontend se Comunica com o Cloudflare Worker:
- Chamadas HTTP REST nativas via metodo central "apiRequest<T>()" em "src/lib/api.ts" (linhas 76 a 185).
- Protocolo: HTTPS direto do navegador para o Worker.
- Autenticacao: Toda requisicao administrativa invoca "getAuthToken()" ("src/lib/api.ts", linha 63) para obter um token JWT assinado do Firebase Auth e anexa no cabecalho "Authorization: Bearer <TOKEN>".
- Tratamento de 401: Se o Worker devolver "401 Unauthorized", o interceptor ("src/lib/api.ts", linhas 114–126) forca a renovacao do token chamando "user.getIdToken(true)" e tenta a requisicao uma segunda vez antes de registrar a falha.
- Sem acesso direto ao Firestore: Nenhuma requisicao passa pelo SDK cliente do Firestore ("firebase/firestore" nao esta instalado no package.json). O Firestore e protegido e lido/gravado unicamente pelo Worker com credenciais de servico.

1.4 Integracao do Firebase Authentication:
- Integrado via Firebase Client SDK Web oficial ("firebase/app" e "firebase/auth").
- Nao ha credenciais de conta de servico (service account private keys) no codigo cliente.
- Persistencia local no navegador ("browserLocalPersistence") em "src/lib/firebase.ts:63".


2. FIREBASE
--------------------------------------------------------------------------------
2.1 Configuracao Utilizada:
Definida em "src/lib/firebase.ts" (linhas 25 a 45) pela funcao "getEffectiveFirebaseConfig()":
- API Key: "import.meta.env.VITE_FIREBASE_API_KEY" com fallback para "localStorage.getItem('zod_firebase_api_key')".
- Auth Domain: "import.meta.env.VITE_FIREBASE_AUTH_DOMAIN" (default: "dashboard-proxy-menu.firebaseapp.com").
- Project ID: "import.meta.env.VITE_FIREBASE_PROJECT_ID" (default: "dashboard-proxy-menu").
- App ID: "import.meta.env.VITE_FIREBASE_APP_ID" com fallback para "localStorage.getItem('zod_firebase_app_id')".
- Messaging Sender ID: "import.meta.env.VITE_FIREBASE_MESSAGING_SENDER_ID".

2.2 Processo de Login e Logout:
- Login ("src/lib/auth.tsx:105-126"):
  1. Verifica se o Firebase esta configurado ("initFirebase()").
  2. Executa "signInWithEmailAndPassword(auth, email.trim(), password)".
  3. Atualiza o estado "user" com a credencial retornada.
  4. Executa "loadAdminProfile(userCredential.user)" para obter o perfil no Worker.
  5. Mapeia codigos de erro comuns ("auth/invalid-credential", "auth/wrong-password", "auth/user-not-found", "auth/too-many-requests") em mensagens amigaveis via "getFriendlyAuthErrorMessage()" ("src/lib/firebase.ts:88-109").
- Logout ("src/lib/auth.tsx:128-140"):
  1. Executa "firebaseSignOut(auth)".
  2. Limpa os estados locais ("user = null", "adminProfile = null", "error = null").
  3. Redireciona a interface imediatamente para a tela de login.

2.3 Como o Token Firebase e Obtido, Armazenado, Renovado e Enviado:
- Obtencao: Funcao "getAuthToken()" em "src/lib/api.ts:63-74", chamando "auth.currentUser.getIdToken(forceRefresh)".
- Armazenamento: O token bruto nao e salvo em variaveis globais nem em cookies desprotegidos. O SDK do Firebase mantem o token em IndexedDB/LocalStorage protegido.
- Renovacao: Gerenciada internamente pelo Firebase Auth a cada ~55 minutos, alem da funcao reativa em "src/lib/api.ts:114-126" que fora "getIdToken(true)" em caso de retorno HTTP 401.
- Envio: Cabecalho "Authorization: Bearer <ID_TOKEN_FIREBASE>" em todas as chamadas autenticadas.

2.4 Como o UID do Administrador e Identificado:
- Extraido da propriedade "user.uid" fornecida pelo Firebase Auth ("src/lib/auth.tsx:67" e "src/pages/ProfilePage.tsx:55").

2.5 Como o Cargo (OWNER, ADMIN ou SUPPORT) e Determinado:
- O cargo NUNCA e definido localmente pelo navegador.
- Apos a emissao do token Firebase, o frontend chama "api.getAdminMe()" ("GET /admin/me").
- Em "src/lib/auth.tsx", linhas 150 a 156:
  const role = adminProfile?.role || null;
  const isOwner = role === 'OWNER';
  const isAdmin = role === 'OWNER' || role === 'ADMIN';
  const isSupport = role === 'SUPPORT';
  const canMutate = isOwner || role === 'ADMIN';
  const canManageAdmins = isOwner;
  const canManageSettings = isOwner || role === 'ADMIN';

2.6 Como a Autenticacao e Validada pelo Servidor:
- O Cloudflare Worker valida a assinatura criptografica do ID Token JWT usando as chaves publicas do Google Identity Toolkit.
- Evidencia confirmada em teste real: Se o token for omitido, o servidor responde "HTTP 401 {\"success\":false,\"error\":\"Token ausente.\"}". Se o token for forjado ou invalido, responde "HTTP 401 {\"success\":false,\"error\":\"Sessao invalida, expirada ou usuario desativado.\"}".

8. PROBLEMA DO BOTAO CRIAR LICENCA (INVESTIGACAO DETALHADA)
--------------------------------------------------------------------------------
Investigacao do motivo pelo qual o botao de criacao de licencas aparece desabilitado para uma conta autenticada com cargo OWNER:

8.1 Condicao Exata que Desabilita o Botao:
1. No menu lateral ("src/components/layout/AppLayout.tsx", linha 105):
   <Button
     variant="primary"
     size="sm"
     className="w-full text-xs"
     onClick={onOpenCreateLicense}
     disabled={!canMutate}
     icon={<Plus className="w-3.5 h-3.5" />}
   >
     Create License
   </Button>
   EVIDENCIA: O botao possui a propriedade explicita "disabled={!canMutate}". Se "canMutate" for falso, o botao fica totalmente desabilitado.

2. Na barra de topo ("src/components/layout/AppLayout.tsx", linha 192):
   {canMutate && onOpenCreateLicense && ( ... )}
   EVIDENCIA: Se "canMutate" for falso, o botao do cabecalho nem sequer e renderizado.

8.2 De Onde Vem a Variavel "canMutate"?
Arquivo: "src/lib/auth.tsx", linhas 150 a 154:
   const role = adminProfile?.role || null;
   const isOwner = role === 'OWNER';
   const isAdmin = role === 'OWNER' || role === 'ADMIN';
   const isSupport = role === 'SUPPORT';
   const canMutate = isOwner || role === 'ADMIN';

8.3 Como "adminProfile" e Preenchido?
Arquivo: "src/lib/auth.tsx", linhas 52 a 81:
   const loadAdminProfile = useCallback(async (currentUser: User) => {
     setProfileLoading(true);
     try {
       const profile = await api.getAdminMe();
       setAdminProfile(profile);
       setError(null);
     } catch (err: unknown) {
       ...
     }
   }, []);

8.4 Causas Tecnicas Comprovadas:

Causa A: Discrepancia de Caixa (Case Sensitivity) no Cargo Retornado pelo Servidor (Mais Provavel)
- Em "src/lib/auth.tsx:151", a comparacao e estrita: "role === 'OWNER'".
- Se o Cloudflare Worker ou o Firestore registrar ou devolver o cargo em minusculas ("owner"), primeira maiuscula ("Owner"), ou "admin":
  "owner" === "OWNER" resulta em FALSE.
  "owner" === "ADMIN" resulta em FALSE.
  Logo, "canMutate" torna-se FALSE e o botao fica permanentemente desabilitado.

Causa B: Descasamento no Envelope da Resposta de "GET /admin/me"
- Em "src/lib/api.ts:180-184", a funcao desembrulha apenas se houver a chave "data":
  if (rawData && typeof rawData === 'object' && 'data' in rawData) {
    return (rawData as { data: T }).data;
  }
  return rawData as T;
- Se o Worker responder no formato:
  {"success": true, "admin": {"uid": "...", "role": "OWNER"}}
  ou
  {"success": true, "user": {"uid": "...", "role": "OWNER"}}
  O "api.getAdminMe()" devolve o objeto raiz (pois nao encontrou "data").
- Assim, "adminProfile.role" torna-se UNDEFINED (pois a chave real esta em "adminProfile.admin.role").
- Como "undefined === 'OWNER'" e falso, "canMutate" torna-se FALSE.

Causa C: Falha na Chamada de "GET /admin/me" (401 / 403 / 500)
- Se o Worker retornar 401 ou 403 na chamada de "/admin/me" (token nao aceito pelo Worker, usuario desativado na base do Worker ou erro interno), o bloco "catch" em "src/lib/auth.tsx:60-62" e acionado.
- O estado "adminProfile" NAO e preenchido (permanece null).
- Com "adminProfile = null", "role = null" e "canMutate = false".

12. COMPATIBILIDADE COM O APK ANDROID
--------------------------------------------------------------------------------
Endpoints que o futuro aplicativo Android devera utilizar para handshake e validacao de licencas:

1. Validar uma key:
   Endpoint: POST /api/v1/licenses/validate (ou /client/verify)
   Payload do APK: {"key": "ZOD-XXXX-YYYY", "deviceId": "HWID_STRING"}
   Resposta esperada: {"valid": true, "status": "active", "expiresAt": "ISO_DATE"}

2. Ativar uma key (1º uso):
   Endpoint: POST /api/v1/licenses/activate
   Payload do APK: {"key": "ZOD-XXXX-YYYY", "deviceId": "HWID_STRING", "deviceModel": "Samsung S24", "deviceName": "Android Client"}
   Resposta esperada: {"success": true, "activatedAt": "ISO_DATE", "expiresAt": "ISO_DATE", "sessionToken": "JWT_OU_TOKEN"}

3. Vincular dispositivo:
   Executado de forma atomica na ativacao ou validacao. Se o limite de hardware for excedido, o Worker devera responder:
   HTTP 403: {"error": "Device limit exceeded", "limit": 1, "current": 1}

4. Verificar licenca:
   Endpoint: POST /api/v1/licenses/check (ou com headers X-License-Key e X-Device-Id)
   Resposta esperada: Status atual ("active", "expired", "suspended", "banned").

5. Renovar sessao / Heartbeat:
   Endpoint: POST /api/v1/licenses/ping
   Payload do APK: {"key": "ZOD-XXXX-YYYY", "deviceId": "HWID_STRING"}
   Acao no Worker: Atualiza o campo "lastActivityAt" no Firestore para acompanhamento no painel administrativo.

6. Encerrar sessao:
   Endpoint: POST /api/v1/licenses/logout
   Payload do APK: {"key": "ZOD-XXXX-YYYY", "deviceId": "HWID_STRING"}
   Acao no Worker: Desvincula a sessao caso o software permita liberacao de slot de hardware.

7. Consultar bloqueios e expiracao:
   Integrado nas respostas de validacao, devolvendo codigo de erro especifico se a chave estiver com status "suspended" ou "banned".
